# agent-godot-wrapper

Pure skill plugin — no binary of its own. It wraps the **external Godot MCP Toolkit** ([NPGameDev/godot-mcp-toolkit](https://github.com/NPGameDev/godot-mcp-toolkit), MIT; bridge: npm [`@npgamedev/godot-mcp-server`](https://github.com/NPGameDev/godot-mcp-server), MIT): the bridge is declared inline in the `mcpServers` block of **both** `.claude-plugin/plugin.json` and `.codex-plugin/plugin.json` under the server key `godotMCP`, and `skills/godot-wrapper/SKILL.md` teaches the agent when and how to drive it. The host agent launches the bridge automatically via `npx`. This repo is the Godot counterpart of `agent-unity-wrapper` and deliberately mirrors its layout, release pipeline and `AGENTS.md` contracts so an agent that knows one can work the other.

## Contracts an agent won't infer from the tree

- **Two processes must be up, and only one of them is ours.** The npm bridge is a thin stdio-to-WebSocket adapter: it forwards tool calls to the **Godot MCP Toolkit editor addon** (`addons/godot_mcp_toolkit/`) running inside a live Godot editor, which listens on `127.0.0.1` in the 6550–6560 band and authenticates every connection with a per-start session token. The addon is installed by the user in the target Godot project (AssetLib, or a copied `addons/` folder, enabled under Project Settings → Plugins). Nothing in this repo can install, start, or health-check that half — if the editor isn't open on the project with the addon active, every tool fails and the fix is user-side. The upstream `project.godot` enable line for a fresh, not-yet-opened project is `[editor_plugins] enabled=PackedStringArray("res://addons/godot_mcp_toolkit/plugin.cfg")`; never edit `project.godot` under a running editor.
- **Editor discovery is registry-based, keyed by project path, and that is what makes worktrees work without any wiring here.** The addon publishes `{project path → port, token path}` into a machine-wide `projects.json` registry; the bridge resolves the editor by matching `GODOT_MCP_PROJECT_PATH` (else `process.cwd()`) against it. A linked git worktree is a distinct absolute path, so it gets its own editor, port and token automatically (upstream "Pattern A"). This is the Godot analogue of `agent-unity-wrapper`'s `UNITY_MCP_STATUS_DIR` status-dir isolation — but it needs **no prepare-script, no managed `start:`/`stop:` block and no adoption hook** to achieve per-worktree isolation, because the toolkit does the keying itself. The one thing it cannot do is two editors on the **same** directory (upstream "Pattern C", registry last-writer-wins + token collision + Godot's own `user://` races) — that is unsupported upstream, not something to work around here.
- **`GODOT_MCP_PROJECT_PATH` travels two different paths, and that asymmetry is deliberate.** The Claude manifest sets `env.GODOT_MCP_PROJECT_PATH=${CLAUDE_PROJECT_DIR}` so the bridge keys on the session's project root (main checkout or linked worktree) regardless of what cwd the host hands it. Codex has no `${CLAUDE_PROJECT_DIR}` (it would arrive as an unexpanded literal and match nothing), so the Codex manifest ships **no `env` block** and the bridge falls back to `process.cwd()`, which Codex sets to the project root. `lint.yml` fails the build if the Claude manifest drops the variable or the Codex manifest references `CLAUDE_PROJECT_DIR`. No other env is set on purpose: port pins (`GODOT_MCP_EDITOR_PORT`, `GODOT_MCP_RUNTIME_PORT`, `GODOT_MCP_LSP_PORT`) must be visible to **both** the editor process and the bridge, and a manifest can only reach the bridge — a pin set here alone would make the bridge dial a port the editor never bound.
- **The version pin is exact on purpose.** `@npgamedev/godot-mcp-server@1.0.4` in both manifests lets `npx` reuse one cached package instead of re-resolving against the registry — the same cold-start reasoning as `agent-serena-wrapper`, `agent-blender-wrapper` and `agent-meshy-wrapper`. The addon and the bridge are versioned independently upstream and negotiate compatibility at connect, so an addon bump does not force a pin bump — but bumping the pin means editing both manifests, re-checking the `$script:ToolkitVersion` constant in `scripts/prepare-godot-worktree.ps1` (not derived from the manifests; it must stay a bridge-compatible addon version) **and** re-checking `SKILL.md`'s tool inventory and group list, which were read off the server's generated tool reference at that version. `lint.yml` enforces that the two manifests never drift apart; it cannot tell you the docs went stale.
- **The tool list is dynamic, and `SKILL.md`'s inventory is hand-maintained against upstream.** 34 tools (plus the 2 meta tools `discover_tools` / `extensions_refresh`) are in the initial `tools/list`; 78 more live in 28 on-demand groups that `discover_tools` activates mid-session via `tools/list_changed`. Current Claude Code handles that notification (upstream verified 2026-07-19, interactive and `claude -p`); a host that does not will never see the on-demand tools. Read-only mode (`GODOT_MCP_READ_ONLY=1`) hides every mutating tool at connect time. A tool *missing from the list* is therefore a not-yet-discovered group or read-only mode — a different failure from a tool that is listed but *fails to call* (editor unreachable). If upstream adds first-class tools or regroups, `SKILL.md`'s framing becomes wrong, not just incomplete.
- **`execute_code` is the plugin's whole risk surface, and it is expression-only.** It evaluates a GDScript *expression* (no statements, no assignment) in the running game (`channel:'runtime'`) or the editor process (`channel:'editor'`), and upstream labels it `DANGER`. The skill's Pitfalls section carries the mitigations (prefer the typed `runtime_set_property` / `node_call_method` tools, small single-purpose calls, no unrequested destructive ops); keep them there rather than assuming host-level permission gating catches it. All file tools are sandboxed to `res://` by the addon's `FileGuard`.
- **Godot environments: `scripts/prepare-godot-worktree.ps1` + `agent-worktree` (ticket #1).** Run once at the root of a target Godot repo (`-RepoRoot`, default git toplevel). It writes `.seretos/worktree-setup.yml` ONLY when absent (existence via `Test-Path`, never read — a pre-existing or zero-byte file is left byte-identical): `version: 1`, `isolation: full`, `start:` steps `default` (headless) and `gui`, one `stop:` step `godot-mcp-stop`. All start/stop logic lives in `.seretos/godot-mcp-launch.ps1`, generated and ALWAYS overwritten (the yml only makes thin calls to it, so fixes reach prepared repos on the next run). It also appends `.godot-mcp/` (pid file, `editor.log`) to the target's `.gitignore` and warns, never fails, on a missing `project.godot` (the addon step is then skipped). It also installs and enables the addon (ticket #4): `addons/godot_mcp_toolkit/` comes from the release zip at `$script:ToolkitVersion` (1.0.4; `-AddonSource` = http(s) URL or local zip path, default the pinned GitHub release asset; a missing local path throws, never falls back to the network), an archive whose `plugin.cfg` is not that version throws and installs nothing, and an addon already at that version is never touched (source not even resolved). An addon at ANOTHER version is left byte-identical, warned about (both versions named) and NOT enabled; `project.godot` is not touched; the user deletes the folder and re-runs to replace it. Then the `[editor_plugins]` entry is added to `project.godot` (idempotent, merges into an existing `PackedStringArray`). `Install-GodotAddon` / `Initialize-GodotAddon` / `Enable-GodotAddon` are callable after dot-sourcing for tests. Editor binary: `$env:GODOT_EDITOR_PATH`, else `godot`/`godot4` on `PATH`, else the step throws. Readiness: the log line `[MCPServer] listening on 127.0.0.1:<port>` or, Windows only, a `by_path` entry in `%APPDATA%/godot-mcp-toolkit/projects.json` that is new or changed relative to before the launch (a stale pre-existing entry never counts); timeout (`-WaitSeconds`, 120) throws and keeps the pid file for `environment_stop`. A live recorded pid short-circuits a second start (two editors on one directory is unsupported upstream). The `project.godot` edit (not the file install) is skipped with a warning while any `godot*` process runs. `-EnableAddon` no longer exists (enabling is the default). Tests: `tests/prepare-godot-worktree.Tests.ps1` (Pester 5.5+); the `Live` tag needs a real editor, a display and `GODOT_EDITOR_PATH` + `GODOT_LIVE_PROJECT` and is run by hand: `pwsh -NoProfile -Command "Invoke-Pester -Path tests/prepare-godot-worktree.Tests.ps1 -TagFilter Live -Output Detailed"`. Still deliberately absent: a `hooks/` adoption hook (a human-started editor is already found via the registry). Headless premises (addon loads, readiness line reaches `--log-file`) are only proven by the Live test.
- **Headless has a documented tool matrix; don't promise screenshots or playtests there.** Under `godot --headless --editor` the file, scene, node, script, ClassDB and project tools work; `game_start` and `editor_screenshot` return `HEADLESS_UNSUPPORTED`, and a headless 4.4+ editor never re-instantiates a reloaded script (stale-instance hints on `node_call_method`). Any non-`--check-only` run of the project with the editor binary (including a headless `--script` test runner) also starts the runtime channel and can take the runtime slot from the game the agent started — set `GODOT_MCP_RUNTIME=0` on such runs.
- **A project's own `.mcp.json` would start a second bridge.** The addon's dock offers to write a `godot-mcp-toolkit` server entry into the project's `.mcp.json`. With this plugin installed that entry is redundant: both would be launched, both would authenticate against the same editor (multi-client is supported upstream), and the agent would see two copies of every tool under two server prefixes. The README tells users to leave it out; the skill tells the agent to flag it if seen. Upstream also notes the dock writes an OS-specific form (`cmd /c npx` on Windows, bare `npx` elsewhere) — this plugin's manifests use bare `npx` on every OS, matching `agent-meshy-wrapper`, which works on current Claude Code for Windows.
- **Release is orphan-branch + marketplace dispatch, with release notes scoped via `src/<TAG>` markers on `main`.** `release.yml` (manual: Actions → release → `version=X.Y.Z`) runs a read-only pre-flight (`.github/scripts/release-preflight.sh`: strict SemVer, HEAD is the tip of the default branch, neither `<TAG>` nor `src/<TAG>` exists, and `src/<PREV_TAG>` does exist when there is a previous release), stamps the version into both manifests, force-pushes an orphan `release` branch holding only install-ready files, and POSTs the same dispatch (`category: skill`, `tags: ["godot","game-engine","3d"]`) to BOTH `seretos-agents/modular-software-factory-staging` (lands straight to main there, no review) and `seretos-agents/modular-software-factory` (opens a review PR there). `main` and `release` share no history, so an orphan `release: vX.Y.Z` commit has no merge-base with anything and `gh release create --generate-notes` would always come back empty. The fix: the workflow pushes `src/<TAG>` onto the actual `main` commit being released (its first remote side effect), and builds notes from `src/<PREV_TAG>`..`src/<TAG>` with `gh api .../releases/generate-notes`. `.github/scripts/marketplace-payload.sh` then forwards that body as the dispatch's `changelog` field via a single `jq -n` (never a heredoc), so hostile characters round-trip byte-for-byte; the key is omitted when there is no changelog. Clients install at the tag `agent-godot-wrapper--vX.Y.Z`; `src/*` markers are internal to notes generation and never shipped or dispatched.
  - **No bootstrap is needed here**, unlike `agent-unity-wrapper` / `agent-meshy-wrapper`: every release of this repo is cut under the marker scheme from the very first one, so `src/<PREV_TAG>` always exists when pre-flight asks for it. If it ever doesn't, pre-flight prints the exact `git tag src/<PREV_TAG> <head_sha>` / `git push` pair to run once by hand, where `<head_sha>` is the head SHA of that release's own successful `release.yml` run — never approximated from timestamps, and never created by the workflow itself (`GITHUB_TOKEN` cannot push a ref at a historical commit whose workflow tree differs from `main`'s tip).
  - `tests/test_release_scripts.py` drives all three scripts against throwaway local repos via `python -m pytest tests/test_release_scripts.py -v` (needs `jq` and, on Windows, Git-for-Windows bash at its default path). `lint.yml`'s `release-scripts` job runs it on an `ubuntu-latest`/`windows-latest` matrix — unlike `validate`, which only runs on `ubuntu` — because these scripts also have to work from a Windows checkout.
- **Required secret:** `ECOSYSTEM_TOKEN` — fine-grained PAT, `Contents: RW` + `Pull requests: RW` on both `seretos-agents/modular-software-factory` and `seretos-agents/modular-software-factory-staging`.
- **`assets/icon.png` and `description.md` are release artifacts, not just repo files.** The dispatch payload sends `raw.githubusercontent.com/${repo}/${TAG}/assets/icon.png` and `.../description.md`, so both must live on the orphan `release` branch at the tagged commit — `release.yml`'s stage step copies them in for exactly that reason. **The current `assets/icon.png` is a generated placeholder** (Godot-blue square with a "G", made with ffmpeg at scaffold time) — replace it with real artwork before cutting v0.0.1 or the listing ships the placeholder.
- **`lint.yml` runs only on `pull_request`, not on every push.** A direct push to `main` triggers no CI at all — safe only once `main` is protected (merge via PR, with a required status check). When branch protection is configured, the required-check context to select is the job id `validate` (the `jobs:` key in `lint.yml`), not the workflow's display name `lint`; the `release-scripts` and `pester` matrix jobs are advisory and, if added, are selected as `release-scripts (ubuntu-latest)` / `release-scripts (windows-latest)` and `pester (ubuntu-latest)` / `pester (windows-latest)`.
- **Depending on an MCP plugin:** declare it under `dependencies` in `.claude-plugin/plugin.json` (`{ "name": "agent-<mcp>", "version": ">=0.0.1 <1.0.0" }`). The Godot bridge is wired directly via `mcpServers` in both manifests (not via `dependencies`), which is why `dependencies` stays `[]`.
- **Alternatives that were considered and not chosen** (so nobody re-evaluates from scratch): [Coding-Solo/godot-mcp](https://github.com/Coding-Solo/godot-mcp) (`@coding-solo/godot-mcp@0.1.1`, most-starred) drives the Godot **CLI** only — launch editor, run project, capture output, 14 tools, no connection to a live editor — so it cannot do the inspect-and-edit loop this plugin exists for; [mkdevkit/godot-mcp](https://github.com/mkdevkit/godot-mcp) has the right addon-over-WebSocket architecture and 173 tools but is unpublished (build from source, no pinnable package) and at 4 commits; [hi-godot/godot-ai](https://github.com/hi-godot/godot-ai) (Asset Store "Godot AI") is comparable in scope, Python/`uv`-based, requires Godot 4.5+, ships opt-out telemetry, and its dock generates the client command rather than documenting a pinnable package name. The toolkit was picked for the pinnable npm bridge, path-keyed worktree isolation, headless support, no telemetry and an active release cadence (1.0.4, 2026-10-14).
